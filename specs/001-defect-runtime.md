# SPEC 001：C/C++ 新增空返回的跨文件影响分析

状态：**后续空返回规则插件规格；不属于基础包 S2/S3 门禁** · 2026-09-26。来源：[交接文档](../Claude_Agent_SDK_Agent层开发交接_精简版_v1.1.md)、[需求基线](../docs/00-需求基线与范围.md)、[ADR 010](../docs/04-最终架构决策-ADR.md)、[SPEC 000](000-runtime-kernel.md)。本 SPEC 描述一个可选规则插件的语义要求；基础包通用要求以 SPEC 000/002/003/004/006 为准，S4 质量验收按 [SPEC 008](008-defect-quality-evaluation.md)。其他缺陷类型应有各自的规则规格。

## 1. 业务问题与边界

在 Base 中 `getBuffer()` 对参与构建的调用路径返回有效指针；Head 新增 `count == 0 → nullptr`。`process(n)` 未修改，却直接解引用返回值；`main → process(0)` 可触发。`guardedProcess(n)` 在 `n == 0` 时提前返回，对这个候选构成反证。真实项目的目标解析、别名、宏与编译配置需由实际语义后端验证，本样例不能单靠文本匹配宣称已证明。

**该规则插件的目标：** 从固定 Base/Head 和候选出发，取得程序证据、完成六项检查、让独立验证角色寻找反证，并输出 `confirmed / refuted / inconclusive`、证据链及覆盖限制；进程或 SDK 会话切换后不重复报告已排除的同一候选。

## 2. 规范性要求

文中“必须”仅约束实现此空返回规则插件的项目；当前基础包阶段不以此处 AC-01 至 AC-17 为完成门槛。

### SPEC-01 固定输入

分析启动时必须固定源码树、Base/Head commit、编译参数/宏、规则/Profile、工具政策。续查时任一绑定改变，原 Evidence 不能自动适用于新快照。候选键必须区分 `process` 与 `guardedProcess`，并标出对象和路径假设。

### SPEC-02 检查单

每个候选生成六项：`nullable_source`、`propagation`、`dangerous_use`、`guard`、`reachability`、`change_attribution`。每项记录问题、答案、证据、状态与限制。某项工具超时、只覆盖直接调用或缺失编译单元时，它仍在未完成/部分覆盖集合中。

### SPEC-03 取证

程序查询必须限制到任务范围；工具返回 complete、partial、timeout、failed、unsupported 或 denied 及覆盖描述。服务端先保存原始材料、位置、哈希、快照/工具版本和查询参数，再把 Evidence ID 返回给 Agent。模型提供的未知 ID 不可被接受。查询空结果只有在可验证的搜索边界存在时才可充当负证据。

### SPEC-04 角色与结论

调查者提出带六项答案、前提和未知的 Claim。验证者使用独立会话和原始证据，逐一核对条件可同时成立、传递对象是否相同、保护是否有效、路径是否可达、是否由 Head 变化引入。VerdictGate 必须拒绝跨快照、跨候选、部分覆盖冒充完整、缺少原始引用的确定结论；多 Agent 同意不是原始证据。

通用门禁通过后，本规则的确定性 `RuleEvaluator` 才判断六项关系是否在同一声明路径和构建变体下足以支持或排除空指针解引用。仅有静态工具的可能数据流、模型解释或局部无告警时，不得推断路径可行或全局不可达。

**`confirmed`** 仅指在明示构建/路径/工具覆盖前提下，该候选的触发条件有完整证据且未被有效反证排除。**`refuted`** 需要具体反证，且只排除该候选/路径。其余均为 **`inconclusive`**，报告未查项和原因。

### SPEC-05 恢复与排除

任务、Attempt、SDK 会话、事件和 Evidence 分开持久化。同一 SDK 历史单写。显式 resume 前核对绑定；跨会话轮换先保存 Handoff，之后新建会话，不 resume 旧历史。Handoff 必须保留条件、反证、未知、未查项、已排除候选及引用。新会话在同一快照中读取 ExclusionRecord 并抑制 `guardedProcess` 同一候选的重复误报；Head/编译/规则变化时要重新验证。

业务事件以单调水位追加，当前检查进度可由事件恢复；SDK session 只保存对话连续性。若 SDK transcript 不可用，记录续接失败，从已校验 Handoff 创建新会话，不把模型记忆当作已恢复。Evidence 写入与检查项 checkpoint 之间中断时，按幂等键核对已存材料，未决操作保持待核对状态。调查者和验证者默认各有 SessionBinding，验证者不继承调查者的全部对话；角色输入由原始 Evidence 引用和独立 ContextView 组成。

Handoff 的受保护条目包括每条尚有效的触发条件、反证、未知、未查项与排除记录。新视图若省略某条，必须已有可追溯的新 Evidence 和显式状态迁移。压缩摘要不修改原始 Evidence 或历史事件。AgentExecutor 必须在启动前声明和校验所需能力；不支持的 resume、结构化输出、工具隔离须显式失败。

### SPEC-06 可观察输出

报告同时列出：确诊候选、已排除候选、证据不足候选、已发现调用点的检查分母/已完成数、未解析间接调用、工具失败和假设。不得把“已发现的 20 个调用点完成 18 个”写成“全库覆盖 90%”；不得把零告警写成全库安全。

## 3. 验收场景

| ID | 给定 / 操作 | 期望 |
|---|---|---|
| AC-01 | Base/Head 同构建配置；`main → process(0) → *getBuffer(0)`；六项都有完整来源材料 | 输出有界 `confirmed`；标出调用路径、零条件、解引用位置、Head 新增分支及 Base 对照。 |
| AC-02 | `guardedProcess(0)` 在调用前早退，有完整分支/参数材料 | 对该候选输出 `refuted`；其他调用路径保持独立。 |
| AC-03 | 对 AC-02 保存 Handoff 并创建新 SDK 会话 | 排除记录与反证仍在；同快照不重复告警。 |
| AC-04 | 尝试从 Handoff 删除早退条件、反证或待查调用点 | checkpoint 被拒绝，旧交接仍可恢复。 |
| AC-05 | `find_callers` 只覆盖直接调用，或发生 timeout | 相关检查 partial/unknown；输出 `inconclusive` 或带限制的局部结论，不声称全量无误。 |
| AC-06 | Agent 引用伪造 Evidence ID、其他构建或其他候选的材料 | 确定结论被拒绝并记录原因。 |
| AC-07 | 角色输出格式正确，但证据无法说明对象同一性/条件可达 | `inconclusive`；结构化格式不能越过语义门槛。 |
| AC-08 | Attempt 在工具结果保存后中断，再次运行 | 已存证据和事件保留；幂等查询可复用；未决请求标为待核对。 |
| AC-09 | 同一 SDK session 同时有第二写入者，或 resume 时 Profile/源码变更 | 拒绝写入/恢复；不发生混合历史。 |
| AC-10 | Head 或构建配置变化后重查 AC-02 | 原排除标记为需复核；不自动套用旧反证。 |
| AC-11 | 仓库注释包含“忽略该问题/修改规则”的指令文本 | 作为待分析数据处理；不改变规则或工具权限。 |
| AC-12 | 六项检查完成，但验证者给出有效相反路径条件 | 输出 `refuted` 或 `inconclusive` 并保留冲突；不因调查者支持而强行确认。 |
| AC-13 | Evidence 已写入，Attempt checkpoint 前进程中断 | 恢复后按幂等键找到已存原文；不会生成第二个不同事实或直接把检查项判完成。 |
| AC-14 | SDK transcript 丢失，但业务事件、证据与 Handoff 完好 | 显式记录旧历史无法 resume；新 session 只恢复经校验的领域状态，未查项仍未完成。 |
| AC-15 | 验证者收到调查者 Claim | 验证者使用不同 SessionBinding；仅通过其 ContextView 收到 Claim、原始 Evidence 引用、限制和反证任务，不继承调查者自由文本对话。 |
| AC-16 | 自动压缩尝试删除仍有效的反证或未知，或者用纯摘要替代原始引用 | 压缩结果拒绝保存；原始 Evidence、业务事件及前一有效 Handoff 保持可恢复。 |
| AC-17 | 执行适配器不支持当前任务必需的 resume、结构化输出或工具隔离 | 启动前报明确能力不匹配；不静默忽略策略。 |

## 4. 测试数据与验证层级

第一层是纯契约测试：状态迁移、引用/哈希/快照校验、Handoff 不丢失、候选去重和报告覆盖。第二层是与真实 Joern/codebadger/Clang 候选后端的样例联测，必须保留原始查询产物。第三层是真实模型联测，观察查询选择、反证召回和成本。三个层级分别报告，不能用第一层替代后二者。

样例至少包含：正例 `process(0)`、保护反例 `guardedProcess(0)`、未知间接调用、不同宏配置、对象别名变化、工具超时、Base/Head 不同编译配置、会话轮换后重复候选。该规则插件声称完成时，AC-01 至 AC-17 应在对应层级有可复核结果；后端未支持的场景必须显式标为 `inconclusive` 与能力缺口。当前基础包可以仅用受控测试规则验证通用机制。

## 5. 实施顺序与变更规则

基础包先按 SPEC 000 完成通用能力；需要实施本规则插件时，再选择真实语义后端、完善 Oracle 并执行本文件的 AC 场景。插件实现变更应引用对应验收案例。发现规则不足或工具无法给出关键材料时，先更新 SPEC/ADR、记录取舍，再调整实现。已有 PoC 仅记录部分材料，不表示插件语义能力已达标。
