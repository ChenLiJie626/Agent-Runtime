# SPEC 008：缺陷检出质量与持续评测

状态：**S4 质量规格；Q-01/Q-02/Q-03/Q-07 首版机制已实现，完整门禁未通过** · 2026-09-26。受 [SPEC 000](000-runtime-kernel.md) 的基础包边界约束，与各规则的语义 Oracle（首个示例为 [SPEC 001](001-defect-runtime.md) 和 [SPEC 005](005-golden-cases-and-oracles.md)）配套。本 SPEC 规定如何证明和持续改进检出质量；不把某个规则硬编码进 runtime，也不回溯改变已通过的 S2/S3 门禁。当前实现与缺口见 [S4 实施记录](../docs/10-S4-质量评测实施记录.md)。

## 1. 质量目标与决策原则

目标是在固定资源预算下提高**可行动缺陷的召回**，同时控制发布告警的误报、遗漏和人工复核成本。不能把“已发现候选中的完成率”称为全库召回，也不能靠大量 `inconclusive` 人为提高 `confirmed` 的表面精度。每次评测同时报告发现、取证、裁决和最终告警四层结果。

每条规则在评测前声明：适用语言与版本、缺陷定义、分析范围（全库或变更引入）、构建矩阵、候选匹配单位、可接受的外部工具和模型、时间/费用上限、主指标及其最低门槛。门槛由首批真实样本的基线与使用场景确定，不能在看到盲测结果后修改。语言/规则跨度很大，因此本 SPEC 不给所有规则设一个无依据的统一百分比。已知正例被有效排除记忆静默抑制属于硬失败，必须单独追踪。

## 2. 可复现评测集与人工 Oracle

固定评测数据只选取**公开、许可证与来源可核验的 C++ 开源项目**，不接入公司内部、客户或其他未公开代码。每个项目固定到具体 commit/PR 及构建配置，保存源码与依赖摘要，并记录许可证、上游链接、公开时间和可再分发范围；无法确认来源或许可的数据不得进入固定集。使用公开源码消除了机密代码授权与外发风险，但不表示其构建脚本或依赖可信：构建、测试和动态验证仍须在无宿主密钥、默认禁网且资源受限的隔离环境运行。

评测集分四层，结果分开报告：

1. **机制夹具**：现有 SPEC 005 的好/坏路径、条件与后端故障变体，用于验证证据和裁决契约；不得代表真实项目准确率。
2. **真实历史缺陷**：从公开 C++ 项目中可重现的修复前/后版本建立样本，保留 issue、触发测试或人工证明、修复提交和同配置构建信息；运行分析时只给模型修复前材料。跨文件、多路径、宏/构建变体和非缺陷近邻均须覆盖。
3. **按项目与时间隔离的保留集**：整个开源项目或较晚时间段不参加规则/Prompt 调参；冻结后盲评。公共样本可能已进入模型训练或检索材料，须记录公开时间、可能污染和排除策略，并用冻结时新近的公开 C++ 提交检验泛化；这些提交及其人工标签在本轮盲评结束前不得用于调参。
4. **真实项目影子运行**：在未参与调参的开源 C++ 项目固定代码快照上运行，告警交由审查者独立核对。未知真值的未告警区域不能计作真阴性，也不能据此计算全库召回。

每个样本有不可变 manifest：公开仓库与提交/PR、上游链接与公开时间、许可证和再分发范围、目标/编译配置、规则版本、代码/依赖/构建摘要、已知缺陷或近邻反例、允许提供给 Agent 的材料、标签来源、发现位置/对象/路径匹配规则和数据分区。至少两名审查者对争议告警给出独立标签并仲裁；标签包括 `true_defect`、`false_alarm`、`unresolved`、`out_of_scope`，另标位置/路径是否匹配及证据是否充分。重复告警先按预先固定的“同一根因与触发路径”规则合并，合并前后数量都报告。

设计依据：[NIST SARD](https://www.nist.gov/itl/ai/ai-standards-and-guidelines-group/sard-design-issues)明确区分人工构造与真实代码，并提醒合成样本能否代表真实工具表现需单独验证；[NIST SATE](https://www.nist.gov/itl/csd/secure-systems-and-applications/samate/static-analysis-tool-exposition-sate)采用真实程序、工具输出和人工分析的评估方法。[Defects4J](https://defects4j.org/)说明可重现修复前/后版本与触发测试的价值，但其 Java 样本不能直接当作 C/C++ 规则成绩。[Martian Code Review Bench](https://codereview.withmartian.com/)及其[开源实现](https://github.com/withmartian/code-review-benchmark)可作为“公开 PR、人工 golden、固定离线集与持续更新集并行”的方法参考；其当前固定离线项目不含 C++，因此不能直接作为本 SPEC 的固定评测数据。

## 3. 指标定义与报告约束

| 指标 | 定义或分母 | 防止的误读 |
|---|---|---|
| 构建/索引覆盖 | 成功分析的目标、编译单元和配置 / manifest 中目标总数；列遗漏原因 | 工具成功退出不等于目标源码均被分析。 |
| 候选召回 | 同时报“可评估样本召回”（匹配候选 / 可评估已知正例）和“召回下界”（可评估命中 / 全部已知正例）；不可评估项另按执行失败类型计数 | 候选没生成时，后续 Agent 无法补救；执行失败不伪装成真实漏报。 |
| 取证召回 | 匹配候选中获得规则要求的可核查路径/条件证据的个数 / 匹配候选 | 区分候选生成与后端证据缺口。 |
| 确认召回 | 同时报可评估样本确认召回和以全部已知正例为分母的确认召回下界 | `inconclusive` 和漏检均不能算确认，执行失败不进入“真正漏报”计数。 |
| 发布精度 | 经仲裁为真实缺陷的去重 `confirmed` / 所有已仲裁的去重 `confirmed`；另报告未仲裁数与将其视为错误的保守下界 | 只挑已核实告警可虚高精度。 |
| 误报负担 | 去重错误告警 / 千行实际扫描代码，或每 1000 行变更代码；同时给每次评审前 K 条的精度 | 能反映使用者面对的告警量。 |
| 弃判与失败 | `inconclusive`、未执行、超时、构建失败分别占已发现候选的比例；未知范围另列 | 不能靠弃判藏漏报。 |
| 排除安全 | 已知正例遭有效 Exclusion 静默抑制的数量；重复误报在换会话后再出现的数量 | 排除记忆不应造成漏检或失效。 |
| 效率 | 每千行/每候选的时间、查询数、模型 token/费用（不可得则 `unavailable`），以及固定预算下的召回/精度曲线 | 不以无限调用换取单点成绩。 |

所有指标按规则、语言、项目、缺陷难度、构建配置和证据后端分层，附原始计数与项目级重采样的不确定区间；样本不足时标为“证据不足”，不发布单一总体百分比。完整扫描与前 K 条告警结果都要保留。对于仅有已知修复缺陷、缺少完整负例标注的数据，不能声称得出真实全库精度；对于仅有告警审查的数据，不能声称得出召回。

执行失败的样本必须使用 `evaluable=false`、`candidate_status=not_run` 和
`evidence_status=not_applicable`；只有 `evaluable=true` 且没有匹配候选的正例才计入
“真正漏报”。报告同时保留 `candidate_recall_evaluable`、
`candidate_recall_lower_bound`、对应的确认召回字段，以及按 `not_run/timeout/`
`build_failure/execution_failure` 拆分的不可评估已知正例计数。

## 4. 提升质量的可替换流水线

1. **宽候选、严证据**：候选发现可以并联变更点、编译器/静态分析诊断、语法与数据流查询及规则专用启发式，保存每路来源和去重映射。前段优先保召回；确定结论仍由规则 Oracle 与通用门禁约束。
2. **面向不确定性的查询规划**：先建立可编译范围与操作覆盖，再针对最可能改变裁决的未知项查询。C/C++ 规则按需要验证调用目标、对象同一、条件可满足、保护支配、路径可达及构建变体；后端不能证明时保持 `partial/unknown`。路径型结果应保留源、汇与中间步骤，[CodeQL 路径查询文档](https://codeql.github.com/docs/writing-codeql-queries/creating-path-queries/)可作后端设计参考。
3. **独立反证与受控裁决**：Verifier 必须能看到原始引用、覆盖限制与相反假设，并核查边界情况；不把模型自信度或多个 Agent 一致当作证据。对 `confirmed`、`refuted`、`inconclusive` 分别统计 Oracle 错误，分析误报根因后再修规则、查询或 Context。
4. **按缺口调用专项角色**：候选发现、调用目标/别名分析、路径条件核查和反证搜索可以由不同角色承担；每个角色只拿所需的 Context 与授权工具。保持确定性协调器和独立最终验证者，不能靠增加 Agent 数量取代证据。专项角色必须在同预算消融中证明改善，否则不成为默认流程。
5. **可选动态验证**：可执行目标经隔离后，用已有测试、定向生成测试、Sanitizer 或模糊测试验证具体路径；真实崩溃/失败作为正证据，未触发不能当作路径不存在。动态验证须保存构建、输入、退出/报告与覆盖。[OSS-Fuzz](https://github.com/google/oss-fuzz)的模糊测试与 Sanitizer 组合可作接入参考，不成为 runtime 强制依赖。
6. **按边际收益分配预算**：记录每轮查询/角色调用消除了哪些未知项、改变了哪些裁决。用固定预算比较查询规划、专项角色和不同后端；停止条件应由证据状态与预算决定。优先级评分只决定先查什么，不越过确定性裁决门禁。
7. **上下文质量回归**：对同一固定证据，比较完整上下文、压缩上下文及换会话后的 Check/Fact/反证/未知与裁决。受保护项丢失、相反条件被合并、负查询缺少搜索边界、有效排除失效或错误复用均单独计数。旧结论被新证据推翻时，保留版本与因果链。

这些做法是本项目从上述公开方法归纳的设计选择，不意味着引用项目已经证明本项目达到某个检出指标。[CodeQL 查询元数据](https://codeql.github.com/docs/writing-codeql-queries/metadata-for-codeql-queries/)将 precision 与结果中真实阳性的比例关联；本项目必须以自己的盲评数据计算，不能直接沿用外部工具标签。

## 5. S4 验收门禁

公开源码与 Runtime 的集成按 [SPEC 009](009-public-source-runtime-integration.md)实施。SDK 角色错误新增 `execution_failure`，与正常 `inconclusive`、超时及构建失败分别计数；源码窗口的完整返回不增加语义取证召回。当前规则版本和首版评测封套保持兼容，报告的失败计数字典允许新增类别；消费者不应依赖固定键集合。

| ID | 验收项 | 必须提交的结果 |
|---|---|---|
| Q-01 | 评测 manifest 与盲评 | 数据全部来自公开 C++ 开源项目；固定输入、可重建构建、上游链接、公开时间、许可证/再分发范围、代码与依赖摘要、项目/时间分区、缺陷/近邻标签及审查仲裁记录；修复信息不泄入分析输入。 |
| Q-02 | 分阶段质量报告 | 第 3 节全部指标的分子/分母、分层、未知与不确定区间；报告版本绑定代码、规则、后端、Prompt、模型实际路由和预算。 |
| Q-03 | 同预算比较 | 至少比较基线后端/规则、Agent 加入后的方案和上一发行版本；有逐组件消融，说明收益、回退及失败样本。 |
| Q-04 | Oracle 与反证 | 正例、近邻反例、部分覆盖、构建差异和路径歧义均按规则规格裁决；错误确认/错误排除有回归样本。 |
| Q-05 | Context/Session 与排除 | 压缩/轮换不会改变有充分证据的结论，不静默丢未知；已知正例不被有效 Exclusion 抑制，重复误报率可量化。 |
| Q-06 | 真实项目影子运行 | 至少一个未参与调参的开源 C++ 目标项目及其构建变体，人工复核告警、记录扫描遗漏；不得把未告警范围当作安全。 |
| Q-07 | 预注册放行条件 | 在盲评前固定主指标、最低精度/召回、误报负担、成本与样本充分性门槛；未达到时保留实验结论并标出瓶颈，不改 Oracle 或分母。 |

先完成 Q-01/Q-02 和首个 C/C++ 规则的可重现基线，再实现第 4 节中由错误归因证明最有价值的扩展。每引入新规则或后端，复用同一评测契约并单独声明适用范围；未经此门禁的插件标为实验性。
