# 技术路线与接口边界

状态：**基础包路线已按通用扩展契约修订；0.2.0 本地发行线已验证** · 2026-09-25。最终选型见[ADR 010](04-最终架构决策-ADR.md)；当前门禁见[规格导航](../specs/README.md)、[SPEC 000](../specs/000-runtime-kernel.md)与[S3 验收记录](09-S3-验收记录.md)。

## 架构切分

```text
调用方 / CLI
  ├─ ProfileResolver ─ Rule / Role / Prompt / ToolPolicy（文件版本化）
  ├─ CandidateIdentity + CheckPlanner ─ 候选精确身份与规则自定义检查图
  └─ AnalysisRuntime
       ├─ SessionService ─ Attempt / SDKSessionBinding / Transition
       ├─ EventJournal + TaskProjection ─ 业务事件 / 当前进度
       ├─ ContextBuilder + ContextManager ─ 工作集 / 交接 / 排除
       ├─ EvidenceService ─ RawEvidence / Claim / Assessment
       ├─ ProgramQuery 协议 ─ 注入的只读查询后端
       ├─ AgentExecutor 协议 ─ Claude Agent SDK 首选适配器
       └─ VerdictGate + RuleEvaluator ─ 通用门禁 / 缺陷规则裁决 / 报告
```

核心模块只依赖自身的领域对象与存储接口。SDK、静态分析工具、数据库引擎是外侧适配器。首版可以在单进程、SQLite 中实现，但从接口上分开证据存储和任务状态。对外导出稳定的领域契约，内部 SQL/SDK 消息形状不直接暴露给引用方。AgentExecutor 只包装 SDK 执行、事件转接和能力声明；**不实现第二套模型与工具循环**。VerdictGate 的通用校验与缺陷类型的 RuleEvaluator 分开，防止把引用有效误认为语义已证明。执行适配器缺少角色所需能力时，启动前报能力不匹配。[领域 API 契约](../specs/002-domain-and-api-contract.md)

### 候选粒度与角色安排

调度单位为“固定分析快照 × 规则 × 规则定义的精确候选身份”。一个候选的必查问题由规则规划，同一调查者按缺口推进；需要专项能力时委派窄范围角色。验证者独立读取**原始证据引用及有限上下文**，并收到调查者的 Claim 作为待证伪对象。程序 gate 决定发布。

### 领域对象与最小字段

| 对象 | 核心字段与不变量 |
|---|---|
| `AnalysisSnapshot` | 仓库、固定源码/构建范围、Profile 哈希、工具版本；差分规则可附 Base/Head；创建后不可暗改。 |
| `CandidateKey` | 规则版本、规则定义的规范化身份字段及快照绑定；身份粒度须区分可能不同的对象与路径。身份不够明确时不能做跨会话排除。 |
| `CheckItem` | 检查名、状态、回答、Evidence 引用、覆盖范围、未知前提；状态更新需可追溯。 |
| `QueryOutcome` | 结果类型、原始内容/指针、位置、查询参数、工具版本、构建快照、覆盖全集及限制。 |
| `RawEvidence` | 服务生成 ID、不可变内容哈希、来源、QueryOutcome、候选关联；模型不能直接写入。 |
| `Claim` | 规则相关触发条件、假设、各检查回答、支持/反驳引用、未知项。 |
| `Assessment` | 验证角色对规则前提与反证的逐项判断及引用。 |
| `ExclusionRecord` | 精确候选键、排除理由、反证引用、适用快照/规则、依赖材料哈希、建立时间、失效状态。 |
| `RoleAttempt` | task、role、状态、事件范围、预算、SDK session ID、启动/结束时间、恢复/轮换关系。 |
| `SessionBinding` | analysis/task/role/attempt、快照、Profile/工具政策、工作目录、SDK session ID、单写租约；默认每角色独立。 |
| `RuntimeEvent` | 单调序号、task/attempt、事件类型、幂等键、相关 Evidence/查询引用、时间；投影可从业务事件重建。 |
| `ContextView` | 面向某角色/缺口的有界模型输入；原始事件和证据保持不变，记录来源/截断/失效条件。 |
| `Handoff` | schema 版本、快照、候选、事实引用、假设、条件、反证、已查/待查/未知、排除、事件水位、下一步。 |

## 对外行为契约

| 能力 | 输入 | 输出 | 拒绝/失败条件 |
|---|---|---|---|
| `create_analysis` | 固定快照和 Profile | analysis ID | 快照/能力冲突、来源不可信 |
| `instantiate_checks` | 规则与候选 | 带必查项任务 | 候选无精确身份、规则缺依赖 |
| `execute_analysis_query` | task、检查、查询与预算 | QueryOutcome；有材料时 Evidence ID | 越权、超时、部分、失败分别记录；落盘失败不可返回 ID |
| `collect_context` | task、当前缺口、token 预算 | 证据引用＋必要代码切片 | 截断未标记、缺少关键条件时拒绝交给模型 |
| `run_role_attempt` | role、task、可选 resume ID | 结构化 Claim/Assessment 或查询请求 | SDK 错误、格式错误、快照漂移显式失败 |
| `checkpoint_investigation` | 当前任务状态 | 经校验 Handoff | 反证/条件/未查项丢失、引用不合法 |
| `rotate_session` | 已保存 Handoff 的安全结束点 | 新 SDK session 映射 | 存在未结束写入或未决工具副作用 |
| `validate_finding` | Claim、Assessment、检查项、Evidence | 有界 verdict 与理由 | 缺证据、跨版本、未覆盖改为 inconclusive |
| `build_report` | analysis ID | 候选、排除、未知与覆盖 | 不允许把局部零告警呈现为全库无缺陷 |

## 状态与恢复

任务执行状态与结论状态是两个维度。执行状态：`pending → running → completed / partial / failed / cancelled`；结论状态：`unassessed → confirmed / refuted / inconclusive`。`completed + inconclusive` 合法，表示流程结束但证据不足。显式重开会生成新的 Attempt，保留原结论历史。

事件先于对外确认持久化。查询请求带幂等键，落盘原始材料后才能发布 Evidence ID。进程崩溃时，恢复器先检查最后事件水位：已完成查询直接复用；未决查询标记为 in-doubt，按工具是否只读及幂等能力选择核对或重试。SDK 会话 ID 仅是交互历史指针；业务状态以任务、证据和事件为准。同一 SDK 历史串行写入。业务事件作为当前进度投影的依据，SDK 消息流只作交互记录。SDK 文档说明 `query()` 默认新建会话、用 `resume` 明确续接，fork 只分叉对话历史。[官方 Sessions](https://code.claude.com/docs/en/agent-sdk/sessions)

同一历史续查的前置条件：快照/Profile/工具政策/工作目录或 SessionStore 仍可用且无并发写入。跨会话压缩的顺序：结束当前安全点 → 生成 Handoff → 验证引用和保留项 → 原子保存 Handoff/Transition → 新建会话并注入 Handoff；失败时旧任务仍可从已保存状态恢复。跨主机恢复若必要，评估 SDK `SessionStore`，不直接搬运或修改 JSONL。[SDK 参考](https://code.claude.com/docs/en/agent-sdk/python)

调查者与验证者默认不同 SessionBinding。验证者接收 Claim 作为待证伪对象，但事实输入只来自原始 Evidence 引用和单独构建的 ContextView；不复用调查者整个 SDK 对话。若 transcript 丢失，恢复器记录历史不可续接，以 Handoff 开新会话，且未完成检查仍是未完成。[Conductor 会话映射](https://github.com/microsoft/conductor/blob/main/docs/workflow-syntax.md#session-continuity-session_key)与[OpenHands 事件持久化](https://docs.openhands.dev/sdk/guides/convo-persistence)提供设计参照。

## Context 选择与压缩策略

1. **先问缺口。** 按 RuleSpec 中未完成的检查项选取证据与代码片段，而不是整库拼接；查询策略由规则和后端决定。
2. **分级内容。** L0 固定快照/规则/候选；L1 必须保留的条件、反证、未查项；L2 相关 Evidence 的定位与短切片；L3 按需取回完整原始材料。原文始终留在 EvidenceService。
3. **压缩操作可验证。** 只合并重复片段和日志，保留规则相关条件、否定、对象身份、失败诊断及其引用。摘要记录来源、覆盖和截断标记；不把“没有找到”改写成“没有”。
4. **排除有生命周期。** 同快照且依赖哈希未变时复用排除；源码或构建范围变化后标为待复核；如果反证只针对某一条路径，不影响邻近候选。跨版本“等价代码”的自动继承留待后续。
5. **未知可解决但有痕。** 交接中的未知项只能以新的 Evidence/Assessment 标为 resolved，不能直接删除；旧 Handoff 永久留存，新的工作集只显示仍有效的未知。
